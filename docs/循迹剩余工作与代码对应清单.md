## 1. 路线动作与进度

文件：application/app_chassis.c；数据较多时再分出app_line_task.c/.h，不提前造通用框架。

数据：每条路线的动作序列、动作数量、当前动作下标。序列使用static const，当前下标使用static。路线号1/2/3只是选择整条路线，不能直接等同于左/直/右。

逻辑：

```c
// 示意，route_plan和line_step的实际定义待路线确认。
action = route_plan[line_step];
result = App_Line_Update(&line_target, dt_s, action);
switch (result)
{
    case LINE_TARGET_READY: /* 复制速度目标 */ break;
    case LINE_FEATURE_DONE: /* 下标推进一次，下一周期使用新动作 */ break;
    case LINE_NO_TARGET:    /* 保持零请求，继续本步骤 */ break;
    case LINE_FAILED:       /* 记录FAULT，禁止继续任务 */ break;
}
```

StartLine1接受任务时下标清零。读取动作前检查是否到序列末尾；到末尾进入等待终点确认的逻辑，不能越界，也不能把动作表耗尽直接当成到达。

缺少：路线1/2/3逐特征的动作顺序，以及“哪些事件算一处特征”。五路探头看不到的特征不应列成一个可自动识别的步骤。

验收：完成事件只推进一次；WAIT不推进；新任务从头开始；表末尾不越界、不自行宣布到达。

## 2. 汇合点不停站衔接，以及真正停车点的完成处理

文件：app_line.c报告终点候选；app_chassis.c处理整段结束与ChassisStatus。

汇合点：路线进度与检测证据确认汇合 → 保持循迹速度 → 交接圆环接近阶段。不进入STOPPING。真正要求停车的位置才给零目标、确认停稳并报告DONE。

重要区分：LINE_FEATURE_DONE只完成一个动作；五路全黑可能是横线或路口；五路全白可能是丢线或计划断线。都不能脱离上下文直接判到达。

缺少：每段的终点图案/信号、传感器与最终停车位置的关系、低速稳定阈值。未确认的距离参数用配置项记录，不能编造。

验收：经过普通路口不报到达；尚未停稳不报DONE；取消不报正常完成。

## 3. 取消、禁用与重新开始

文件：app_chassis.h/.c，B调用侧保持同一RobotTask顺序。

按B回复新增App_Chassis_RequestStop（最终签名按完整协议核对），所有自动任务共用。App_Chassis_Stop现有函数只清控制状态，不等于完整任务取消接口。

逻辑：取消 → 撤销任务运动请求、清循迹记录和路线进度、完成标志置0 → 停止处理 → 停稳后IDLE；故障恢复规则与B统一。enabled=0时立即走现有禁止输出路径，不能只依赖缓慢斜坡。失联/急停后不得自动从旧动作继续冲出。

验收：转弯途中可取消；取消不产生FEATURE_DONE/DONE；重新Start从新任务起点执行；取消覆盖隧道。

## 4. 普通丢线恢复和观察超时

文件：app_line.c；时间/速度/角速度放app_config.h。

逻辑：普通FOLLOW确认丢线 → 进入有限时恢复 → 利用最后有效偏差方向进行受限找线 → 连续确认清晰线路后恢复FOLLOW；超过配置时间返回LINE_FAILED。没有可靠方向时不猜左右，停止并按已约定策略处理。

观察阶段必须有明确的超时和退出策略，不能在WAIT或复杂图案中无期限等候。确认计数与恢复计时分别管理。

注意：当前直角入口要求中间无黑连续确认，期间零速度请求；传感器图案可能随减速停住，恢复入口是否能继续推进需结合实车位置验证，不承诺现有启发式能覆盖所有直角。

验收：一次闪烁不触发大动作；找回后清旧记录；找不到明确失败；已有TURN不被普通丢线逻辑抢走。

## 5. 第二段计划断线衔接

文件：app_line_task或app_chassis组织LINE2任务；app_line.c复用基础跟线和恢复。

逻辑：确认到达允许断线的进度窗口 → 无线时维持受限方向/速度跨越 → 新线连续确认 → 继续LINE2；超出最大时间或距离而未见线则失败。窗口以外无黑仍按普通丢线处理。

缺少：各断线位置、长度范围、进入窗口的可靠依据。时间/里程估计只能提供窗口，不能单凭全白判断是计划断线。

验收：第一段丢线不会误走断线策略；LINE2非断线区域同样找线；跨过后窗口关闭；多处断线各自可确认。

## 6. 绕完整一圈

文件：建议application/app_lap.c/.h组织内部过程，复用line组件/基础跟线；app_chassis分派LAP。

逻辑：确认入口 → 沿圆弧循迹 → 累计独立进度证据 → 满足一整圈条件后允许确认出口 → 出口稳定确认 → 停车/完成。

应按规则绕完整一圈，旧方案180度描述作废。单凭外探头再次变白或一次时间到不能证明一圈。轮速里程/航向估计可提供辅助，但打滑存在误差；需要结合可识别入口出口和最小进度窗口。

缺少：圆环实际路线、入出口特征、可用航向来源及精度。一圈的判断依据先定，随后选最简单实现。

验收：半圈不退出；重复入口不误算出口；持续丢线或超时可失败/取消。

## 7. 隧道与灯色

文件：建议application/app_tunnel.c/.h保存隧道过程，app_chassis提供协议入口和查询。

按B回复：每轮Run前SetLight(color, valid)，color为0/1/2/3；valid由B判断消息过期与非0。只在双方确认颜色含义后写颜色枚举，不能擅自假设1/2/3对应哪种灯。

逻辑：接近入口 → 按灯色决定等待/允许通过 → 可靠确认完全进入并锁存本次inside → 低速穿过 → 确认车体完全驶出 → 停车/完成。进入前与已在隧道中遇到灯色变化/失效的策略要分别明确。

IsTunnelInside表示本任务曾可靠完全进入；IsArrived以完全驶出为完成。取消统一RequestStop，不新增隧道专用取消入口。

缺少：入口出口检测依据、车体尺寸与检测点关系、颜色编码、入内后失效策略。

验收：红灯/未知灯不擅自进入；未完全驶出不报到达；inside每次新任务清零；途中可取消。

## 8. B侧接口与串级控制接通

文件：app_chassis.h/.c、app_robot.c或B自动流程文件；实际函数名/参数按完整最新协议核对，不用本清单示意名替换已约定接口。

对接：StartLine1、绕圈启动、隧道启动、第二段启动、对应停止/统一RequestStop、GetStatus、IsArrived、SetLight、IsTunnelInside。Start每次进入步骤只调用一次并判断是否接受；查询每10ms；失败退出、不阻塞while等完成。B整机步骤与A内部探头阶段保持独立。

当前外环：偏差P → 底盘wz目标；内环：四轮速度PI。若坚持外环也使用PID，需要先统一偏差单位和输出单位、限幅、dt、状态切换时复位积分；是否加D取决于实测噪声，不为了串级名称强加I/D。该工作并入本包，不另造全套控制框架。

运动链：任务速度请求 → 运动许可与限制 → 斜坡 → 麦轮解算/限速 → 实测轮速 → 四轮PI → BSP输出。

验收：状态仍为双方约定7个；没有下层调用上层；手动和自动不同时写目标；外环输出有角速度限制、内环输出有驱动限制；B步骤超时与A动作超时分工明确。

## 9. 联合模拟、实车准备和自动运动解锁

文件：持久测试目录（正式接入时确定位置）、app_config.h、必要的BSP配置。

模拟序列覆盖：直行/左右直角、特征反复、动作切换、计数中断、停线与普通路口区分、丢线/断线窗口、圆环半圈与一圈、灯色失效、取消、新任务、故障保持。测试要成为可重复运行的工程资产，不只留在本次会话tmp。

实车前逐项核对：探头左右顺序与黑白电平、电机轮位和正方向、编码器正方向与每轮一圈计数、轮径与轮距、AT8236真实接线、PWM频率/有效电平、控制周期、PI与速度限制。参数0占位未完成时禁止宣称可行驶。

只有任务逻辑和必要参数就绪、基础电机验证通过后，才按明确许可解锁自动运动。解锁不是简单删掉motion_allowed=0。

验收：完整工程编译、主机逻辑测试、单轮与低速底盘检查有结果；最终赛道表现必须靠实车验证，不能用编译通过替代。

## 最终每10ms一次的执行关系

```text
B：更新灯色/任务请求/运动许可
  ↓
App_Chassis_Run：按当前任务选择本周期流程
  ├─ LINE1/LINE2：按进度取动作 → App_Line_Update
  ├─ LAP：执行绕圈阶段
  └─ TUNNEL：执行灯色与进出阶段
  ↓
处理结果：有目标 / 暂无目标 / 特征完成 / 整段结束条件 / 故障
  ↓
运动许可 → 斜坡 → 麦轮 → 四轮测速与PI → BSP
  ↓
B查询7状态和协议完成信号，决定下一个整机步骤
```
