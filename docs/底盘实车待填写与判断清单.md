## 1. 当前进度和边界

**第一至第七部分的通用任务流程骨架已接入，不必继续为这些阶段重复搭框架。但还不能理解成“代码全部写完，只差调参”。**

已经有：四轮测速、速度比例积分控制、斜坡、麦轮解算、电机驱动链；基础循迹、特征观察、直角转弯、普通丢线恢复；第一段与第二段循迹、计划断线跨越、绕圈、隧道的周期流程；连续交接、取消、停稳确认和故障处理。

尚缺五类工作：

- [ ] 现场检测代码：确认当前处于什么位置、是否达到阶段条件。
- [ ] 动作安排：路线二后续动作、入环与出环动作，以及后半段直角是否需要独立步骤。
- [ ] 策略确认：隧道入内后灯色失效如何处理、无可跟线路时怎样通过。
- [ ] 配置和标定：尺寸、计数、速度、控制参数和超时。
- [ ] 与电控乙接通，并完成实车验证；检测不可靠时仍可能需要调整代码。

目前 `CHASSIS_AUTO_MOTION_READY` 为零，多项物理参数为零；这些是占位，不能直接作为实车参数。

## 3. 现场判断：逐项填写

统一填写入口是 `application/app_track.c` 的 `App_Track_Read(TrackInput *input)`。

三种结果必须区分：

- `TRACK_UNSET`：判断还没实现或依据未确认。
- `TRACK_NO`：判断已实现，但本周期条件不满足。
- `TRACK_YES`：本周期确认条件满足。

不要把尚未实现的项直接填成“满足”来绕过等待。只要求当前阶段使用的项可信，不要求所有字段在所有位置同时有效。

| 勾选 | 字段 | 要确认的事实 | 填写判断前需要采集的信息 |
|---|---|---|---|
| [ ] | `merge` | 第一段已到三路汇合位置 | 三条路线各自进度、汇合前后五路序列、与普通路口的区别；这里继续走，不停车 |
| [ ] | `gap_window` | 当前处于允许计划断线的路段 | 第二段断线的位置、进入与离开窗口的可靠依据；不能一直置为满足 |
| [ ] | `gap_start` | 已到当前断线的跨越起点 | 起点前后图案、位置依据，必要时测距离；不能只凭一次全白 |
| [ ] | `line_found` | 跨越后出现候选新线 | 新线图案、探头位置、反光与误检情况；流程会再做连续确认 |
| [ ] | `line2_end` | 第二段真正要求停车的位置已到 | 终点特征、车体与探头的距离、最终停车位置；不能把普通横线当终点 |
| [ ] | `lap_entry` | 已到圆环入口参考位置 | 入环前后的线路序列、路线方向、参考位置 |
| [ ] | `lap_full` | 已有独立证据证明完成一整圈 | 满圈依据、入口与出口的区分、进度窗口；如果需里程或航向，还需补相应数据计算 |
| [ ] | `lap_exit` | 已沿正确出口离开圆环 | 出口动作完成后的图案和位置；不要只凭再次看到入口就确认 |
| [ ] | `tunnel_entry` | 已到入口前的等待参考位置 | 隧道口位置、探头和车头距离、允许停靠位置 |
| [ ] | `tunnel_inside` | 整个车体已经完全进入 | 车长、参考检测点到车尾的关系、可靠位置证据；车头进去不等于整车进去 |
| [ ] | `tunnel_outside` | 整个车体已经完全驶出 | 出口参考点、车尾离开所需距离、出口后的路线 |
| [ ] | `tunnel_pass_allowed` | 已进入阶段是否允许继续行驶 | 与乙确认入内后红灯、黄灯、未知灯、数据失效时的具体策略 |

### 判断编写时必须补充的上下文

当前 `App_Track_Read()` 只接收结果指针，没有收到当前任务、路线和动作进度。它目前也不读探头。

- [ ] 确定各判断实际需要哪些输入：当前五路结果、当前阶段、路线编号、动作序号、必要的里程或航向。
- [ ] 如果确实需要这些输入，由应用层内部通过参数传入或保存明确的上下文；检测模块不反向调用底盘上层查询私有状态。
- [ ] 若检测自身有跨周期记忆，补上新任务、取消、禁用和重新开始时的复位。
- [ ] 避免基础循迹和现场判断各读一次却被当成同一帧；需要组合判断时，统一采样或明确数据时序。

这部分可能要修改内部接口，不是仅把十二个字段逐个赋值就一定够用。对电控乙的公开函数名继续沿用双方协议。

### 每个判断建议记录的实测表

| 项目 | 待填写 |
|---|---|
| 判断名称与适用阶段 | 待填写 |

**不预设“全黑就是进入隧道”，不预设“全白就是计划断线”，不把时间到了直接当成绕完一圈。**

## 4. 动作表和路线进度

填写入口：`App_Track_GetAction(TrackAction part, uint8_t route, uint8_t step, LineAction *action)`。

| 勾选 | 查询种类 | 当前情况 | 需要补充 |
|---|---|---|---|
| [ ] | `TRACK_LINE1_ACTION` | 入口已有：路线一左转、路线二直行、路线三右转；入口为第零步 | 路线二从第一步开始的真实动作顺序、各步对应的可检测特征、动作结束后的持续跟线安排 |
| [ ] | `TRACK_LAP_ENTER_ACTION` | 未填写，当前返回尚未配置 | 各路线的入环方向；当前调用动作序号为零 |
| [ ] | `TRACK_LAP_EXIT_ACTION` | 未填写，当前返回尚未配置 | 满圈后出环方向；当前调用动作序号为零 |

路线一、三入口之后目前采用普通连续循迹。这是已有设计假设，仍需实车确认弯度和探头覆盖足够。

动作表需要明确“特征完成后下一步是什么”，不能以动作表耗尽代替终点确认。连续跟线使用 `LINE_ACTION_FOLLOW`；处理一处直行特征使用 `LINE_ACTION_STRAIGHT`，二者不同。

### 第二段与隧道后的直角

当前第二段在断线处理以外调用普通连续循迹，没有单独的逐路口动作表。

- [ ] 在路线图上标出后半段的每处直角和实际行驶方向。
- [ ] 若实际需要“确认路口后执行左转或右转”，在第二段任务中增加对应动作步骤，复用已有基础转弯函数。
- [ ] 只有实测普通偏差循迹确实能通过时，才能保持当前连续跟线安排。

因此，后半段如果存在必须主动选向的直角，这仍是待补代码，不属于单纯调一个比例系数。

## 5. 隧道运动策略

- [ ] 实测隧道内是否仍有可用线路，灰度探头是否能正常区分黑白。
- [ ] 当前隧道流程复用基础循迹，只在获得有效循迹目标时改为隧道速度；不是已经实现了无线行驶。
- [ ] 如无可用线路，先确定航向和距离依据，再补相应运动策略，不能仅将判断填为满足。
- [ ] 明确未知灯、红灯、黄灯、有效绿灯在入口前的行为。
- [ ] 与乙确认入内后灯色变化或失效策略，并实现 `tunnel_pass_allowed`。

当前实现入口前要求本周期有效绿灯，才继续接近或驶入。若规则要求先接近等待点再等绿灯，应先核对并调整此处顺序，不默认现有顺序已适合场地。

## 7. 硬件核对，不是只填应用参数

- [ ] 五路探头从车体左到右的编号、引脚、黑白电平与 `App_Line_Read()` 一致。
- [ ] 实测探头高度、横向位置、中心探头前突量和约两厘米线宽下的图案。
- [ ] 实物麦轮安装方向与当前解算约定相符。
- [ ] 四个实际轮位与电路板电机接口映射正确。
- [ ] 各轮正输出方向和编码器正计数方向一致，并对应车身前进方向。
- [ ] 实际驱动为当前使用的方案；按原理图核对输入、电源、有效电平和零输出行为，不套用旧驱动引脚结论。
- [ ] 核对四路脉宽调制频率、引脚和定时器映射；用测量确认输出。
- [ ] 核对编码器轴位置、线数、倍频、减速比；手动转轮一圈记录计数。
- [ ] 测速周期和传入时间间隔一致；两个采样之间真实计数变化小于计数范围的一半。
- [ ] 先验证单轮，再低速验证前进、横移和旋转，随后闭环和自动任务。

## 8. 与电控乙需要接通的内容

- [ ] 初始化完成后再提交任务；启动返回一只代表接受，不代表完成。
- [ ] 阶段启动只在进入该阶段时提交，检查返回值，不每周期反复重启。
- [ ] 同一控制任务顺序提交灯色、任务或运动许可，再调用底盘周期入口；核对实际周期和传入时间。
- [ ] 灯色编码沿用当前协议：未知零、红一、绿二、黄三；有效性由乙根据新消息和时效判断。
- [ ] 每次周期执行都会消费灯色有效性，不能靠一次绿灯长期放行。
- [ ] 汇合点不停：`IsArrived()` 可为一但状态仍为运行；乙需及时启动绕圈阶段。
- [ ] 出环不停：`IsLapDone()` 可为一但状态仍为运行；允许接第二段或隧道，实际顺序由双方路线安排确认。
- [ ] 连续交接只允许第一段到绕圈、绕圈到第二段或隧道；其他切换需符合空闲或完成状态。
- [ ] 真正停车点先减速并确认停稳，再报告完成；不能把交接到达与停稳完成混为一谈。
- [ ] `IsTunnelInside()` 表示本任务曾确认完全入内，不表示已经驶出；取消和新任务会清除。
- [ ] 取消统一用 `RequestStop()`；取消不报告正常完成，故障不自动恢复。
- [ ] 乙先检查故障，再消费完成信号；核对双方各自超时的职责。
- [ ] 手动与自动目标写入互斥；禁用、失联、急停、重新开始均进行联合测试。

当前乙侧 `app_robot.c` 仍存在自动流程和安全请求待接通项，不能因为甲的函数已经存在就认为整机对接完成。

## 9. 测试文件处理结果

检查时 `tests` 内仅有两个文件，没有可删除的无用测试文档：

| 文件 | 用途 | 处理 |
|---|---|---|
| `tests/auto_flow/test_flow.c` | 用模拟现场结果检查任务转换、交接、断线确认、取消、禁用、停车和灯色消费 | 保留 |
| `tests/auto_flow/run.ps1` | 编译运行上述电脑端测试，结束后清理临时程序 | 保留 |

当前固件构建只收集应用、组件、板级目录的源文件，测试目录不编入固件，不占单片机运行内存和程序空间。

运行方式：在工程根目录的终端执行 `& .\tests\auto_flow\run.ps1`。脚本默认使用本机现有编译器，也支持用 `-Gcc` 指定编译器路径。

这些测试替换了现场检测和基础循迹，证明的是模拟条件下的任务流程，不证明真实探头、直角和完整赛道一定能通过。

## 10. 推荐后续顺序

1. 把本清单第八节与乙核对，先接通任务调用和连续交接。
2. 有实物后先完成硬件核对和基础参数，跑通单轮、测速、低速底盘。
3. 记录五路序列，验证直线、弯道、直角、丢线，再填写动作表及现场检测。
4. 分别验证第二段断线、完整一圈、隧道出入和灯色策略。
5. 把实际复现的异常补成回归用例，最后联合跑完整路线。
